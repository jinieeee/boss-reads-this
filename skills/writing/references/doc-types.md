# 문서 종류별 형식

## 형식표

| 문서 | 기본 독자 | 서술 / 개조 | 두괄 / 미괄 | 기본 골격 |
|---|---|---|---|---|
| 기획서 | 임원·결정권자, 다른 직군 동료 | 개조 위주. 배경만 짧게 서술 | 두괄 | 배경 → 목표 → 범위 → 일정·리소스 |
| 보고서(주간·결과) | 임원·결정권자 | 개조 | 두괄 | 결론 → 근거 → 이슈 → 다음 할 일 |
| 장애 보고서 | 임원·결정권자, 같은 팀 개발자 | 개조 + 타임라인 표 | 두괄 | 영향 → 원인 → 조치 → 재발 방지 |
| 제안서 | 임원·결정권자 | 섞어 씀 | 결정권자에게는 두괄. 반대가 예상되는 독자에게는 미괄 | 문제 → 대안 비교 → 제안 → 기대 효과 |
| 회의록 | 다른 직군 동료(참석자) | 개조 | 두괄(결정 사항을 맨 위에) | 결정 → 할 일(담당·기한) → 논의 내용 |
| 메일·공지 | 받는 사람. 모르면 다른 직군 동료 | 짧은 서술 | 두괄 | 요청·알릴 내용 → 배경 → 기한·문의처 |
| 기술·스터디 문서 | 신규 입사자·학습자 | 개조 + 표·도식·코드 | why부터 | 아래 "스터디 문서" 참고 |
| 사용 가이드·매뉴얼 | 고객·외부 | 개조 + 화면 캡처 | 두괄 | 아래 "사용 가이드·매뉴얼" 참고 |
| 인프라 문서 | 같은 팀 개발자 | 개조 + 표 | 두괄 | 아래 "인프라 문서" 참고 |
| 화면설계서(SB) Description | 같은 팀 개발자 | 짧은 개조 | - | 아래 "SB Description" 참고 |
| 회고·칼럼 | 다른 직군 동료 | 서술 | 미괄 | 상황 → 겪은 일 → 깨달은 점 |

기본 독자는 요청이나 대화에서 독자를 알 수 없을 때 쓰는 값이다. 독자 이름은 `references/readers.md` 표와 같다. 독자가 둘이면 앞에 적은 쪽이 맨 앞을 읽는 사람이다.

메일은 보내는 수단이지 문서 종류가 아니다. 메일에 담는 내용이 장애 보고, 결과 보고, 회의록이면 그 문서 종류의 형식을 따르고, 메일 형식으로는 맨 앞 인사와 맺음만 더한다. 형식표의 "메일·공지" 행은 요청이나 안내 하나를 전하는 메일에만 쓴다.

## 고르는 기준

**서술식 vs 개조식**

- 개조식: 훑어보고 다시 찾아볼 문서. 항목끼리 순서나 대등 관계가 분명할 때.
- 서술식: 이유와 맥락이 이어져야 하는 글. 설득, 사과, 회고, 짧은 메일.
- 개조식이어도 항목 하나하나는 조사와 연결어미를 살린 문장으로 쓴다. 명사만 늘어놓거나 `→`, `/`, `=` 같은 기호로 낱말을 대신하면 오히려 읽기 어렵다.
- 서술식과 개조식은 문서 전체가 아니라 문단마다 고른다. 서술식 문서 안에서도 아래 내용은 개조식이나 짧은 명사형으로 쓴다.
  - 서로 이어지지 않는 사실이 둘 이상 나란히 있을 때(대상, 위치, 조건)
  - 순서대로 따라 하는 절차
  - 두 가지 이상을 견주는 내용. 표가 더 나으면 표로 쓴다.
- 작성일, 버전, 작성자, 대상 같은 문서 정보는 문장으로 풀지 않고 명사형으로 쓴다. 이때는 "명사만 늘어놓지 않는다" 규칙을 적용하지 않는다.
- 표 칸은 서술식 문서 안에서도 개조식으로 짧게 쓴다. "~합니다", "~입니다"로 맺지 않고 명사형(~함, ~없음, ~필요, ~변경)으로 맺는다. 칸이 길어지면 옆 칸과 견주기 어렵다.
  - 연결어미와 조사는 뜻이 통할 만큼 남긴다. `→`, `/`, `=` 같은 기호로 낱말을 대신하지 않는다.
  - 칸 안에 사실이 둘이면 마침표로 끊는다. 이유·결과를 괄호에 넣지 않는 규칙(`style-rules.md` 6절)은 표 칸에도 적용한다.
  - 표 밖의 본문 문장은 문서 형식대로 쓴다.

| 나쁜 예 | 고친 예 |
|---|---|
| 2026-11-09 에 V2.0 기준으로 작성했습니다. | 2026-11-09 작성 |
| 이 기능은 관리자와 편집자가 쓸 수 있고, CA 화면에서 설정하며, 운영 서버에는 아직 없습니다. | 항목 셋으로 나눈다. "쓰는 사람: 관리자, 편집자", "설정 위치: CA 화면", "운영 서버: 아직 없음" |
| 표 칸: "지금은 `API_DEPLOY_CONTROL_DIR`을 설정하지 않아 꺼져 있습니다." | 표 칸: "`API_DEPLOY_CONTROL_DIR` 미설정으로 꺼져 있음" |

**두괄식 vs 미괄식**

- 두괄식: 독자가 바쁘거나, 결정을 내려야 하거나, 결론만 읽고 넘어갈 수 있는 글. 업무 문서는 대부분 여기에 든다.
- 미괄식: 결론을 먼저 말하면 독자가 거부감을 느끼는 글, 경험을 따라가야 이해되는 글.
- 헷갈리면 두괄식으로 쓴다.

## 스터디 문서

기술을 공부하며 정리하는 문서(컨플루언스 스터디 페이지 등).

- 섹션마다 **왜 필요한가**로 시작한다. 이 기술이 어떤 문제를 풀고, 없으면 무엇이 안 되는지 한두 줄로 쓴다.
- 옵션·설정을 설명할 때는 기능과 함께 **쓸 때와 안 쓸 때의 차이**를 비교한다. 표에 "안 쓰면 / 쓰면" 열을 둔다.
- 서술형 문단 대신 개조식으로 쓴다. 글로 풀 수 있는 내용도 되도록 표, 코드 블록, 도식으로 보여 준다.
- 4단 구조를 따른다.
  1. 개념: 핵심 정의 한두 줄
  2. 상세 개념: 동작 원리, 구성 요소, 옵션 비교
  3. 사내 적용 사례: 실제 코드·설정에서 어떻게 쓰는지, 확인한 값
  4. 실습: 명령어, 다시 따라 할 수 있는 절차
- 아이콘(이모지)은 쓰지 않는다.
- 이해에 도움이 되면 도식을 직접 판단해서 만들어 붙인다.

## 인프라 문서

인프라 상위 문서에는 인프라에 꼭 필요한 내용만 쓴다.

- 넣을 것: 서버·네트워크·접속 경로, 클러스터·namespace·자원(quota, requests, 디스크), 배포 경로(잡, Argo CD, 레지스트리), 백업. 모두 현재 상태 기준.
- 뺄 것: 앱 내부 구현(워커 종류·개수, 프레임워크 버전), 기능 검증 결과, 고객사 화면·브랜드·데이터 작업, 앱 설정 튜닝값.
- "알려진 한계와 남은 일", "하위 문서 목록" 같은 절은 상위 문서에 넣지 않는다. 필요하면 하위 페이지로 쓴다.

## SB Description

화면설계서의 Description 칸.

- 조사와 수식어를 살린 짧은 개조식으로 쓴다. 명사만 늘어놓는 축약은 하지 않는다.
- 문장 끝은 명사형으로 짧게 맺는다(~표시, ~비활성, ~불가). 문장 안의 연결어미(~하고, ~하며, ~하면)와 조사는 뜻이 통할 만큼 남긴다.
- `→`, `/`, `=` 같은 기호로 낱말을 대신하지 않는다. 화면에 보이는 문구를 따옴표로 인용할 때는 원문 기호를 그대로 둔다.
- 다른 시트를 가리킬 때는 "N페이지" 대신 화면 ID로 쓴다. 페이지 번호는 시트를 옮기거나 지우면 틀어진다.
- 같은 화면의 모달·Alert 시트도 각자 고유 ID를 둔다.
- 버튼 활성 조건과 동작은 기본 화면에, 문구와 표시 조건은 모달·메시지 시트에 한 번만 쓰고 서로 ID로 가리킨다.
- 다듬으라는 요청이 없으면 사용자가 손댄 문장은 그대로 둔다.

| 나쁜 예 | 고친 예 |
|---|---|
| 미선택 시 버튼 비활성 / 선택 → 활성 | 스타일을 고르지 않으면 [다음] 버튼 비활성, 하나 이상 고르면 활성 |
| 3페이지 모달 노출 | 클릭하면 `RD-S007 · 결과물 저장 모달` 표시 |

## 개발 문서의 코드

스터디 문서, 장애 보고서, 인프라 문서, MR·PR 설명처럼 코드를 다루는 문서에 함께 적용한다.

**언제 넣는가**

- 글로만 쓰면 독자가 코드를 열어 봐야 이해할 수 있을 때 코드 블록을 넣는다. 동작 원리, 원인, 고친 방법을 설명하는 곳이 여기에 든다.
- 설명 없이 코드만 붙이지 않는다. 코드 블록 바로 위에 이 코드가 무엇을 보여 주는지 한 줄로 쓴다.

**어떤 코드를 넣는가**

- 실제로 고친 코드를 저장소에서 그대로 가져온다. 설명하려고 새로 쓰거나 기억에 의존해 다시 쓰지 않는다.
- 고친 내용은 `diff` 블록으로 보여 준다. 바뀐 줄 앞뒤로 이해에 필요한 줄만 남기고 나머지는 `// ...`로 줄인다.
- 코드 블록 위에 파일 경로를 적는다. 사내 문서면 GitLab 파일 링크나 MR 링크를 건다. 커밋 해시는 쓰지 않는다.
- 개념을 설명하려고 만든 예시 코드는 실제 코드와 섞지 않는다. 블록 위에 "예시"라고 밝힌다.
- 비밀값은 `<자리표시자>`로 바꾼다. 고객사가 읽는 문서에는 사내 저장소 경로와 링크를 넣지 않는다.

## 사용 가이드·매뉴얼

한 페이지가 아니라 상위 페이지 아래 여러 하위 페이지로 나뉜 문서다. 페이지마다 제목이 있다.

- 상위 페이지: 가이드 전체의 목적과 대상, 하위 페이지 목차, 문의처를 둔다.
- 하위 페이지: 그 페이지에서 할 일과 절차만 쓴다. 문의처와 대상처럼 상위 페이지에 이미 있는 내용은 되풀이하지 않는다.

## 컨플루언스 페이지

컨플루언스에 올리는 문서. 다른 문서 종류(스터디, 인프라 등)의 규칙과 함께 적용한다.

컨플루언스는 올리는 곳이지 문서 종류가 아니다. 독자는 문서 종류와 올리는 공간으로 정한다. 고객사가 보는 공간이나 고객사에 넘길 가이드는 독자를 고객·외부로 둔다.

**고객사가 읽는 페이지**

- 사내 약어와 코드명을 쓰지 않는다. 고객사가 쓰는 메뉴 이름과 화면 이름으로 쓴다.
- 고객사가 열 수 없는 GitLab, Jira, 사내 컨플루언스 페이지는 링크로 걸지 않는다. 아래 "원문 링크" 규칙보다 이 규칙이 먼저다.

**패널**

| 내용 | 매크로 |
|---|---|
| 문서 목적, 작성일자·버전, 정본 위치 | 맨 위 info 패널 |
| 빠뜨리면 장애나 데이터 손실이 나는 주의 | warning 패널 |
| 알아 두면 좋은 예외, 팁 | note 패널 |
| 특정 상황에서만 보는 긴 절차 | expand |

- 패널 하나에는 최대 세 줄까지만 쓴다. 문장, 개조식 항목, "2026-11-09 작성" 같은 명사형 줄, 줄을 바꿔 쓴 "구분: 값"을 모두 한 줄로 센다.
- 가이드·절차 문서의 기준은 작성일자와 버전(예: 2026-11-09, V2.0)으로 쓴다. git 커밋 해시는 본문에도 패널에도 쓰지 않는다. 독자가 해시로 할 일이 없고, 저장소가 바뀔 때마다 낡은 값이 된다.
- 패널에는 독자가 그것만 읽고 넘어가도 되는 주요 내용만 넣는다. 목적과 결론, 기준, 꼭 지킬 주의가 여기에 든다. 배경, 근거, 참고 문서 목록, 상세 설명은 본문으로 뺀다.
- 세 문장을 넘으면 문장을 줄이지 말고 덜 중요한 문장을 본문으로 옮긴다.
- 패널은 한 화면에 두세 개까지만 둔다. 본문 전체를 패널에 넣지 않는다.
- expand는 패널이 아니므로 문장 수 제한을 두지 않는다.

**코드 블록**

- 무엇을 넣을지는 "개발 문서의 코드" 절을 따른다.
- 명령어, 설정 파일, 경로가 두 줄 이상이면 code 매크로에 넣고 language를 지정한다(bash, yaml, json, sql 등).
- 한 줄짜리 파일명, 키, 명령은 본문 안 인라인 코드로 쓴다.
- 비밀번호, 토큰 같은 비밀값은 코드 블록에도 쓰지 않는다. `<자리표시자>`로 둔다.

**원문 링크**

- 다른 컨플루언스 페이지를 번호나 제목 글자로만 쓰지 않는다. 페이지 링크(`ac:link`)로 걸고, 특정 절을 가리킬 때는 앵커까지 건다.
- 저장소 파일을 근거로 들 때는 GitLab 파일 링크를 건다.
- Jira 이슈는 이슈 키로 링크한다.
- 링크 글자는 가리키는 대상의 이름으로 쓴다. "여기", "링크" 같은 글자는 쓰지 않는다.

| 나쁜 예 | 고친 예 |
|---|---|
| 설정 키의 뜻은 364 「고객 설정 파일」을 봅니다 | 설정 키의 뜻은 [364. 고객사 하드코딩 공통화 › 고객 설정 파일](페이지 링크+앵커)을 봅니다 |
| info 패널에 목적, 기준, 정본, 참고 문서 3개, 배경을 모두 씀 | info 패널에는 목적, 기준, 정본만 쓰고 참고 문서는 본문 첫 절로 옮김 |
